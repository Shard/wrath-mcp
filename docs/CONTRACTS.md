# Observation and Action Contracts

These two contracts are what make a server-side control module defensible as a client-equivalent agent surface. The module enforces them; the SDK assumes them; this document states them.

## Observation contract

The agent may observe exactly what a real 3.3.5a game client connected to this character could observe, and nothing else.

The test for any field is: which `SMSG_*` packet would carry this to a client? If there is no such packet, the agent does not get it.

Allowed, with the client's limits:
- Own character: level, XP, health, power, position, buffs and debuffs, cooldowns, inventory (with the keyring and the currency token slots, the PRIVATE `PLAYER_FIELD_KEYRING_SLOT_1` / `PLAYER_FIELD_CURRENCYTOKEN_SLOT_1` update fields on self, which the server counts toward a quest's items), equipment, gold, quest log with objective progress text, known spells, skills, glyphs (the slots on `SMSG_TALENTS_INFO`), the character sheet (stats, armour, resistances, attack power, crit, block, dodge and parry: PRIVATE update fields on self), stand state and shapeshift form, rested XP (`PLAYER_REST_STATE_EXPERIENCE`) and exploration XP (`SMSG_EXPLORATION_EXPERIENCE`), reputation as the client shows it, achievements earned (the login list plus each own earn, with the names and points a client reads from its own DBC), whether the character is in a rest area (`resting`, the `PLAYER_FLAGS_RESTING` bit on the `playerFlags` the module already serves — the same resting icon a client draws on its XP bar), whether it is in combat or stunned (`inCombat`, `stunned`, the `UNIT_FLAG_IN_COMBAT` and `UNIT_FLAG_STUNNED` bits on self), or mounted (`mounted`, the `UNIT_FLAG_MOUNT` bit on self), its combo points (`SMSG_UPDATE_COMBO_POINTS`), a Death Knight's runes (`SMSG_CONVERT_RUNE` and the rune list on its own `SMSG_SPELL_GO`), its channel (`MSG_CHANNEL_START` / `MSG_CHANNEL_UPDATE`), its totems (`SMSG_TOTEM_CREATED`, removed by raw `CMSG_TOTEM_DESTROYED`), the breath, fatigue and fire bars (`SMSG_START_MIRROR_TIMER` / `SMSG_STOP_MIRROR_TIMER`), its proficiencies (`SMSG_SET_PROFICIENCY`), its ammo (`PLAYER_AMMO_ID`, set by raw `CMSG_SET_AMMO`) and self-resurrection spell (`PLAYER_SELF_RES_SPELL`, cast by raw `CMSG_SELF_RES`), and whether a flight is in progress (`taxiFlight`, the `UNIT_FLAG_TAXI_FLIGHT` bit on self) and when it lands (`taxiEta`, from the duration of the flight's own `SMSG_MONSTER_MOVE`, the spline a client flies itself along; the landing puts position at that spline's last point, and then on the ground under it, the drop a client's own physics make and report as `MSG_MOVE_FALL_LAND`) with the server's reply to the last flight request, whether a flight master's node is known and a new path learned (`SMSG_TAXINODE_STATUS`, `SMSG_NEW_TAXI_PATH`), the flight master's window when one is opened through its gossip (`SMSG_SHOWTAXINODES`: the node it stands at and the nodes this character has visited, named and placed from the client's `TaxiNodes.dbc`; never the route table), and where the hearthstone goes (`SMSG_BINDPOINTUPDATE`, at login and after every innkeeper bind).
- World objects: creatures, players, game objects, and items within update range, with the fields a client receives (name, level, health as the client sees it, faction, position, hostile/neutral/friendly, target, and the state a client reads off the unit's flags: in combat, stunned, skinnable, lootable, tapped, tapped by you; the spell a unit channels and at what; sitting and shapeshift form). Hostile, neutral and friendly are the client's own reaction calculation over its `FactionTemplate.dbc` and `Faction.dbc` rows for the unit's faction, client-cache knowledge served beside the faction id; quest-scripted forced reactions (`SMSG_SET_FORCED_REACTIONS`) are not yet applied. Objects outside update range or not yet sent by the server are not visible.
- Portals in view (operator decision of 2026-10-20, [Shard/WrathBench#276](https://github.com/Shard/WrathBench/issues/276)): the map-transition portals within the map's visibility range (the range every object is sent at). A dungeon entrance or exit is scenery and an area-trigger volume, never a unit or game object, so no packet names it, yet a player sees the portal and knows where it leads. Its position is the volume's centre from the client's own `AreaTrigger.dbc`; its destination is the map the server's `areatrigger_teleport` row names, with that map's `Map.dbc` name and instance type. The operator ruled the destination client-perceivable: what a player sees in the portal and reads off its zone text. Only triggers that lead to another map are served; the arrival point never is, and nothing beyond view range is.
- Target: what the client shows for the current target.
- Events: combat log entries (immunities and environmental damage among them, `SMSG_SPELLORDAMAGE_IMMUNE`, `SMSG_ENVIRONMENTAL_DAMAGE_LOG`), spell results and pushbacks (`SMSG_SPELL_DELAYED`), loot windows, quest updates, gossip menus with their body text (`SMSG_NPC_TEXT_UPDATE`, answering raw `CMSG_NPC_TEXT_QUERY`), played time and the server's clock on request (`SMSG_PLAYED_TIME`, `SMSG_QUERY_TIME_RESPONSE`, answering raw `CMSG_PLAYED_TIME` and `CMSG_QUERY_TIME`), vendor lists, chat, death and release, zone changes, errors the client would display.
- Map knowledge: nothing beyond what the SDK provides or a harness supplies as its own reference material. The agent does not get the server navmesh or spawn tables. One bounded exception, operator decision of 2026-10-05: when a `move_to` fails `target_off_mesh`, the result names the walkable point nearest the *requested* point within 20y, or that there is none — a statement about the agent's own guess in a failure hint, the way a client's click-to-ground lands beside a point that is not ground. The agent still cannot query the navmesh: nothing answers a point that was not asked for as a destination, and a sweep of such answers only ever describes the agent's own guesses.

Not allowed, even though the server knows them:
- Exact mob health when the client would show a percentage.
- Aggro and leash radii, loot tables, respawn timers, spawn coordinates, quest objective coordinates read from the database, creature AI state. The objective areas the server sends in `SMSG_QUEST_POI_QUERY_RESPONSE` are a packet the client receives, and are served (below).
- Objects beyond update range or behind the server's visibility checks.
- Anything about other sessions' characters beyond what a nearby player would see.
- The module's own diagnostics: the global session count, the packet-drop census and the world-load store counts. `GET /health` serves those to loopback (operator) callers only; the network view is liveness-only (see PROTOCOL.md).

Ambiguity resolves toward the client: if it is unclear whether a client could see something, it is not served until someone checks.

## Action contract

Every action is dispatched as the client opcode a real client would send, through the character's `WorldSession` handler. The module never calls server internals (`Player::CastSpell`, `MotionMaster`, teleport commands, GM commands) to perform an action on the agent's behalf.

The action set:
- Session: create character (class, race, name), log in, log out.
- Movement: move to position (client movement packets along a path), stop, face, jump is not required.
- Targeting: set target, clear target.
- Combat: start and stop auto-attack, cast spell by id (with optional target), cancel cast. A cast, or an item's use, may also carry an item target (`TARGET_FLAG_ITEM`, an item the character holds) and a ground target (`TARGET_FLAG_DEST_LOCATION`, a point the caller gives in full), in the target block a client writes; the server judges both.
- Interaction: interact with object, open gossip with NPC, select gossip option.
- Quests: accept quest from questgiver, complete and choose reward, abandon quest. Quest-start items: an item whose template starts a quest and has no on-use spell is not a `CMSG_USE_ITEM` — the core drops spell id 0 as unknown — so `use_item` on it sends what a client's right-click sends, `CMSG_QUESTGIVER_QUERY_QUEST` with the item's own guid as the questgiver, and the accept names the item guid the same way; the server offers with `SMSG_QUESTGIVER_QUEST_DETAILS`. The quest id is the item template's (client-cache knowledge, as the on-use spell id already is).
- Loot: open loot, take item, take money, take all. Chests: the core ignores `CMSG_GAMEOBJ_USE` on a chest and drops `CMSG_LOOT` on a game object guid, so a chest is opened as a client opens one — `CMSG_CAST_SPELL` of the lock's Opening spell (`SPELL_EFFECT_OPEN_LOCK`) at it, then the same store/money/release sequence.
- Vendor: list, buy, sell, repair.
- Inventory: equip item, use item, destroy item. Items that open for loot: an item whose template has `ITEM_FLAG_HAS_LOOT` (a clam, a lockbox) is opened, not used, so `use_item` on it sends what a client's right-click sends, `CMSG_OPEN_ITEM`, and its window is emptied with the same store/money/release sequence.
- Chat: say. Party chat, yell and whisper are the same `CMSG_MESSAGECHAT` sent through the raw passthrough, which the SDK's `say` builds for its `type` option (the channel a party's agents coordinate on); the other chat types stay raw until a trajectory earns them a helper. Chat the server would run as a command (the core's own `.`/`!` prefix test) is refused, on every chat path and whatever the account, as a GM account is, unless the session was created with the GM opt-in, which only the holder of the port secret can give (operator decision, Mark, 2026-10-29; module/PROTOCOL.md, "POST /session", `allowGm`). By default the module serves player use only: a GM's command set, or commands granted to a player account in `rbac_account_permissions`, are actions no player's client has, and an agent never reaches them by accident.
- Death: release spirit, reclaim corpse, spirit healer resurrection (the graveyard fallback when the corpse is unreachable).
- Stuck: the Help frame's "I'm stuck", which a client sends as `CMSG_CAST_SPELL` of spell 7355 with no target. Every character knows it and may cast it alive or dead; the server's `Spell::EffectStuck` decides the move (a body is released, a ghost goes to the graveyard nearest it, the living go home by Hearthstone or a few yards over). It is a cast by id, so the action set does not grow; the SDK's `unstuck()` sends it only on a second call (operator decision, 2026-10-28).
- Trainers: list, buy spell.
- Talents: learn talent, learn preview talents.
- Raw passthrough: one allowlisted client opcode with a caller-built body, queued verbatim into the stock handler. The allowlist (module/PROTOCOL.md, "raw") holds only opcodes a stock client sends in ordinary play whose handlers do nothing a non-GM client could not do, and excludes movement, session lifecycle, anything already covered by an action, and anything GM-gated. It is the escape hatch the SDK surface philosophy promises ([WrathBench `docs/METHODOLOGY.md`](https://github.com/Shard/WrathBench/blob/master/docs/METHODOLOGY.md#the-model-surface), "The model surface"): a way for a trajectory to show need before a surface is built, not a second path to existing actions. Replies reach the agent only through the existing event whitelist — "I sent it and saw nothing" is precisely the evidence that earns a tap or a helper — and a raw opcode recurring in trajectories is the signal to give it an action. The allowlist is the agent's action surface, never a place to spend for operator convenience.

Observables added under the same test (each is a packet the client receives): the spellbook (`SMSG_INITIAL_SPELLS`, `SMSG_LEARNED_SPELL`, `SMSG_REMOVED_SPELL`, `SMSG_SUPERCEDED_SPELL`), cooldowns (`SMSG_SPELL_COOLDOWN`, `SMSG_COOLDOWN_EVENT`, `SMSG_CLEAR_COOLDOWN`) and talents (`SMSG_TALENTS_INFO`). Own-teleport arrivals ride the same test (`MSG_MOVE_TELEPORT_ACK`): the server tells a client where it landed after a Hearthstone or graveyard port, so the agent is told too. Spell rank and name ride the spell rows as client-cache (Spell.dbc) knowledge, the same way item-template fields already do. No new observation is involved in the state cache keeping a window open: the vendor list, the trainer list and the loot window are already-whitelisted events, and folding the latest of each into the cache — as the gossip menu and the flight master's window already are — only stops the agent from having to re-ask for what it was already told. The loot window closes on the release the server sends; nothing served closes a vendor or trainer frame, so those read as "last observed" with their seq and ts, never as "open".

Achievements and flight paths ([Shard/WrathBench#8](https://github.com/Shard/WrathBench/issues/8)): `SMSG_ACHIEVEMENT_EARNED`, the login `SMSG_ALL_ACHIEVEMENT_DATA` (completed block only) and `SMSG_ACTIVATETAXIREPLY` are whitelisted, with name and points as client-cache (Achievement.dbc) knowledge, and the flight is the `UNIT_FLAG_TAXI_FLIGHT` bit on self. Flight activation stays raw (`CMSG_ACTIVATETAXI`), and the flight master's window (`SMSG_SHOWTAXINODES`) is whitelisted with node names as client-cache (TaxiNodes.dbc) knowledge. The innkeeper bind rides the same test: `SMSG_BINDER_CONFIRM`, `SMSG_BINDPOINTUPDATE`, `SMSG_PLAYERBOUND` whitelisted, `CMSG_BINDER_ACTIVATE` raw. The node positions those same `TaxiNodes.dbc` rows carry are contract-clean too: they are the client's own cache, drawn on the flight map a client shows, so they pass the test the node names already pass. No decision withholds them, and they are served beside the names on every window (built when an observed trajectory's flight use asked for them, which is the observed-need rule for surface growth and nothing more); the window carries the mask's nodes only, as a flight map draws what the character has discovered. The route table stays out either way — a chain of hops is the caller's to name, sent as the client's own `CMSG_ACTIVATETAXIEXPRESS` and judged by the server. Achievements and flight use are observed, never inferred: the module never asks the server's achievement manager anything — a run's achievements are what its own packets said — and a flight "ends" when the consumer sees the flag flip, because no packet says so and inventing an event for it would be the SDK asserting an outcome the wire never gave. Progress *toward* an achievement is deliberately not tapped: it is not a milestone, and the criteria stream is chatter a client renders and a consumer has no derivation for.

Skills, the talent frame, item tooltips and reputation: the skill pane is the `PLAYER_SKILL_INFO` update fields on self (3.3.5 has no skill opcode) named from `SkillLine.dbc`; the talent frame is a client-local read of `Talent.dbc`/`TalentTab.dbc` answered on request, with the learned ranks staying `SMSG_TALENTS_INFO`'s; the respec is the trainer's `MSG_TALENT_WIPE_CONFIRM` whitelisted and echoed raw; the item tooltip is the rest of `SMSG_ITEM_QUERY_SINGLE_RESPONSE` decoded; reputation is `SMSG_INITIALIZE_FACTIONS`, `SMSG_SET_FACTION_STANDING` and `SMSG_SET_FACTION_VISIBLE` whitelisted, named from `Faction.dbc` with the race/class base a client adds. An item's random property ("of the Bear") is the PUBLIC `ITEM_FIELD_RANDOM_PROPERTIES_ID`, `ITEM_FIELD_PROPERTY_SEED` and enchantment-slot update fields every client in range receives, named from `ItemRandomProperties.dbc` / `ItemRandomSuffix.dbc` / `SpellItemEnchantment.dbc` the way skills are from `SkillLine.dbc`; the suffix's stat amounts are the client's own arithmetic on those fields (allocation × seed / 10000), done in the SDK. All of it is client-cache knowledge over packets the client already receives; nothing here reads server state a client lacks.

Pets, party, mail, bank and trade: the pet frame is `SMSG_PET_SPELLS` (the control bar the core sends on every change), the pet's own unit update fields — including the PUBLIC owner fields `UNIT_FIELD_SUMMONEDBY` / `CREATEDBY` / `CHARMEDBY` and `UNIT_FIELD_PETNUMBER`, which every client in range receives — and the `CMSG_PET_NAME_QUERY` a client fires on the pet number, answered by `SMSG_PET_NAME_QUERY_RESPONSE`; `SMSG_PET_ACTION_FEEDBACK`, `SMSG_PET_TAME_FAILURE`, `SMSG_PET_CAST_FAILED`, `SMSG_PET_NAME_INVALID` are whitelisted and the pet client opcodes are raw, as is dismissing a companion (`CMSG_DISMISS_CRITTER`). The party is `SMSG_GROUP_INVITE`, `SMSG_GROUP_LIST`, `SMSG_PARTY_COMMAND_RESULT`, `SMSG_GROUP_DECLINE`, `SMSG_GROUP_UNINVITE`, `SMSG_GROUP_SET_LEADER`, `SMSG_GROUP_DESTROYED`, and the party frames of a member out of sight, `SMSG_PARTY_MEMBER_STATS` and `SMSG_PARTY_MEMBER_STATS_FULL` (status, health, power, level, zone, a map-less x, y and visible auras: the packets a client draws its party frames from while the member is out of range, with `CMSG_REQUEST_PARTY_MEMBER_STATS`, the frame's own refresh, raw and never sent by the SDK on its own; operator decision, Mark, 2026-10-21); the mailbox is `SMSG_SHOW_MAILBOX`, `SMSG_MAIL_LIST_RESULT`, `SMSG_SEND_MAIL_RESULT`, `SMSG_RECEIVED_MAIL`; the bank is `SMSG_SHOW_BANK`, `SMSG_BUY_BANK_SLOT_RESULT` and the PRIVATE `PLAYER_FIELD_BANK_SLOT_1` / `PLAYER_FIELD_BANKBAG_SLOT_1` update fields on self (the client holds them from login); trade is `SMSG_TRADE_STATUS` and `SMSG_TRADE_STATUS_EXTENDED`. Every one is a packet the client receives; spell and item names ride along as client-cache knowledge. `SMSG_PET_MODE` is never sent by the core, so nothing stands in for it.

Group loot rolls and item text: the roll frame is `SMSG_LOOT_START_ROLL`, `SMSG_LOOT_ROLL`, `SMSG_LOOT_ROLL_WON`, `SMSG_LOOT_ALL_PASSED` and `SMSG_LOOT_MASTER_LIST` whitelisted, the vote `CMSG_LOOT_ROLL` raw; reading a book or letter is `SMSG_READ_ITEM_OK` / `SMSG_READ_ITEM_FAILED` and the page chain `SMSG_PAGE_TEXT_QUERY_RESPONSE` whitelisted, with the item query now serving the template's `pageText` so the SDK can send the `CMSG_PAGE_TEXT_QUERY` a client sends on its own; the player-written text on a mailed letter is `CMSG_ITEM_TEXT_QUERY` raw and `SMSG_ITEM_TEXT_QUERY_RESPONSE` whitelisted. Names and text only; nothing here carries a coordinate.

Quest objective areas (operator decision, [Shard/wrath-mcp#4](https://github.com/Shard/wrath-mcp/issues/4)): `CMSG_QUEST_POI_QUERY` is raw and `SMSG_QUEST_POI_QUERY_RESPONSE` whitelisted. It is how a stock client draws a quest's objective areas on its world map and quest tracker: per quest in the log, polygons of world x/y points on a map, each marked with the objective it is for or the turn-in. Server-supplied coordinates delivered over a client opcode pass the observation test like any other packet, and the server answers only for quests the character's log holds. What stays out is the database read directly: the module looks up no quest, spawn or objective location on the agent's behalf, so the area is all the agent gets, and an objective's creatures and objects are still found only by being seen.

Dungeons and the party's kills and resurrections: the map a character is on is named from the client's `Map.dbc` with its `InstanceType` (open world, party dungeon, raid, battleground, arena) — client-cache knowledge over the map id `SMSG_LOGIN_VERIFY_WORLD` and `SMSG_NEW_WORLD` already carry, served beside the zone names on `WB_AREA` and `WB_SESSION_STATE`, as the client reads the same row when it loads the map. The kill record is `SMSG_PARTYKILLLOG`, which the core sends the killer's party, or the killer alone, for a kill that rewards a player: the killer's and the victim's guids, nothing more. A resurrection offer is `SMSG_RESURRECT_REQUEST`, the packet a client draws its "accept resurrection?" dialog from (the caster, and whether accepting brings sickness), answered by `CMSG_RESURRECT_RESPONSE` on the raw allowlist. A dungeon portal that refuses a ghost because its corpse is not inside answers with the bodiless `SMSG_CORPSE_NOT_IN_INSTANCE`, whitelisted as the event it is. Each is a packet the client receives.

Melee swing errors: `SMSG_ATTACKSWING_NOTINRANGE` and `SMSG_ATTACKSWING_BADFACING` are whitelisted. The test they pass is the plain one: the server sends both to the attacking client, and the client shows each as an on-screen error, so a player with auto-attack armed out of range or facing away is told why no swing lands — they are "errors the client would display", above. Both packets are bodiless and the events carry nothing more than the wire did: no victim, no distance, nothing read from server state. The core latches them, and a consumer must read them that way: one event per change of error state, nothing when the error clears, and the latch resets only on a swing that passes both checks or at login — not on stopping the attack or changing target. The absence of an event therefore does not mean the character is in range or facing its target; only a swing says that. No "cleared" event is synthesized, because the wire has none and inventing one would be the module asserting an outcome it was never told. `SMSG_ATTACKSWING_DEADTARGET` and `SMSG_ATTACKSWING_CANT_ATTACK` are never sent by the core at the pinned commit, so nothing stands in for them.

The reattach replay (module/PROTOCOL.md, "/events") is not a new observation. A client holds its own update fields, its items, its spellbook, talents, reputations, achievements, bind point and the objects in view for the life of its connection, and a client that dials in again is handed all of it by the login path; the bench client's connection is its WebSocket, so a subscriber that asks for the replay on a character already in world is that client dialling in again, and the module hands it, and it alone, the same packets, built by the core's own login senders and visibility builder, without adding a field. Nothing in it is served that the login did not serve, and nothing reaches the world: no packet is broadcast and no server state moves. Before it, a restarted sandbox saw less than a client would (an empty bag, no quest log, no health), which was a false observation, not a narrower one.

Deferred until single-player play is validated: the auction house (`CMSG_AUCTION_*` is not allowlisted and no auction reply is tapped), the dungeon finder, guilds, battlegrounds and PvP, dual spec and equipment sets. Pet talents and the stable are also unserved: nothing has asked. None of these is a contract question — each is a packet a client receives and an opcode it sends — they are scope, held back so the surface a solo character needs is finished and validated first.

## Pathing

The module resolves "move to position" into the client movement packet sequence a client would send along a navmesh path, using the server's mmaps. This is the one place the module does work a client would do locally, and it is done so that movement is correct rather than privileged. The agent still cannot query the navmesh directly; it asks to go somewhere and either arrives or gets a typed failure event (`no_mesh`, `target_off_mesh`, `start_off_mesh`, `path_incomplete`) — the z-ladder, the subdivision retry, the long-corridor plan and the end a move's start can reach are the module's, not the agent's, because they are pathing detail. So is the edge past the end of the mesh (operator decision, 2026-10-28): when a route stops short of a request below it, the module walks on toward the request over the ground a client walks, judged from the terrain, model and liquid geometry a client has, and falls from the edge, which is answered as any ledge is (`drop`, walked with `force`); it describes only the line to, and the route to, the agent's own request. A move the world ends is typed the same way rather than left to inference: `transferred` when a portal or trigger changed the map, `teleported` when a same-map teleport moved the character. Two more pieces of client-local behaviour ride on the mover under the same test: areatriggers — the module reads the client's own `AreaTrigger.dbc` from the data volume and sends `CMSG_AREATRIGGER` on entering a volume, exactly as a client does without the player choosing to, so portals, exploration credit and inns happen to the character as consequences the agent observes; and transports — when the mover's position is inside a transport's model bounds, movement packets carry the `ONTRANSPORT` flag and transport-relative offset a client's physics would produce, so the character is a passenger the server carries. Neither is an agent action; both are what a client does on its own.

## Audit

Every observation served and every action dispatched is logged at the module boundary with session id and timestamp, one file per session and UTC day (module/PROTOCOL.md "Audit log"). Files and records name the session by a fingerprint of its token, never the token (operator decision, 2026-10-29), as the worldserver log does. It is the ground truth for the wire while it is kept, and it is kept for a window, not for good: by the operator's decision of 2026-10-18, audit and server logs are operational records with a retention of a few days (set by the deployment), pruned by age and never while a session still writes. The long-lived per-run record of what went on the wire is the one a harness keeps from the sandbox's action log (`docs/ARCHITECTURE.md`, "The action log"), which is what a result claim points at.

## Control-surface authentication

Stated precisely so nobody re-derives it the hard way. The control surface is
a token-bearer one: `POST /action` and `DELETE /session` act on the session
their token names, and the snippet sandbox can reach the port. Without a
credential of its own, a snippet in run A could therefore drive or tear down
run B — across the per-run isolation boundary a harness measures inside.

The floor that closes that (`module/PROTOCOL.md`
"Authentication" is the authority on the served surface):

- **A secret on the port.** Every request and every `/events` upgrade carries
  `Authorization: Bearer`; the module refuses anything else with `401` before a
  route runs, and does not listen at all without a configured secret. There
  is no unauthenticated path and no backward compatibility.
- **A per-run secret the module issues, before the session exists.** The
  sandbox host (`mcp/src/main.ts`, or a harness's own), holding the port
  secret, calls `POST /lease` for the run's
  token and receives a random secret bound to that token and the run's
  account. That secret is the only credential the snippet child gets. It is
  honoured for the token's own `/session`, `/action`, `DELETE /session` and
  `/events` (validated against the lease, so the SDK still subscribes before it
  creates and loses none of the login burst) and refused everywhere else: for
  another token, and for leasing, `/characters` and `/character-delete`.
  **The ambient SDK client is the only holder of that secret, and a hand-built
  client is refused** (operator, 2026-10-19). A snippet cannot read the secret
  — it is struck from the child's environment once the one client has read it,
  and lives in a private field absent from the client object's enumerable
  surface, its reflection and its stringification — and cannot open its own
  connection to the module: the child's `fetch` and `WebSocket` refuse every
  host, the module's included, so the only module connection is the ambient
  client's own transport. A second `WrathClient` a snippet constructs, or a
  raw request it assembles, therefore has no credential and no transport.
  Session lifecycle (`createSession`, `deleteSession`/logout) is reachable only
  through the ambient client, bound to this run's own token and account; it was
  a second, hand-built client opening a session the sandbox host did not follow that
  this narrowing closes ([Shard/WrathBench#74](https://github.com/Shard/WrathBench/issues/74)). The kernel's per-port TCP rule still lets
  `node:net`/`Bun.connect` open the module's port, but with no credential to
  read such a connection authenticates nothing.
- **Token-to-account and token-to-character binding.** A leased token lands on
  its lease's account, with its lease's GM opt-in, whatever the body says, and the first create that
  succeeds under it binds the character; a later same-token create for another
  is refused. A snippet cannot delete any character — its own included — and
  cannot open a session on any account or character but the one it was
  launched as.
- **The snippet child can reach the module's port and nothing else it was
  not given.** The child is exec'd under a Linux Landlock ruleset
  (`mcp/src/sandbox/confine.ts`; `docs/ARCHITECTURE.md`, "The sandbox") that the kernel enforces however a
  snippet reaches: reads only of what the snippet runtime needs to run, so
  `.env`, the repo root, the home directory, `/tmp`, `/dev/shm` and every
  other process's `/proc` entry answer `EACCES`; TCP
  connections only to the port in the run's module URL, and no listening
  socket; no executable but the interpreter itself, so a spawned shell or
  `curl` never starts; and, where the kernel has Landlock scopes, no signal
  to a process outside the sandbox. The sandbox refuses to start rather than
  run unconfined. This is the client-fidelity boundary as much as a security
  one: a game client talks to the game server, and a snippet that could reach
  a database, a harness's own services or an orchestrator would be observing and
  acting through something no client has.

  Stated plainly, what the kernel rules do not cover: Landlock's TCP rules
  are per port, not per host, so the child may dial the module's port on any
  address; UDP (name resolution is its legitimate use), raw sockets and other
  socket families are outside Landlock. Closing those is the deployment's
  network policy — the sandbox child's egress is the module's port on the
  module's host and DNS, and nothing else is a legitimate destination.

The account allowlist (`WrathBench.Accounts`) gates only which accounts the
module serves; it is not caller authentication. What this does not do: it does
not authenticate the operator's own tooling to anything finer than "holds the
port secret", and the audit log remains the record of what each token actually
dispatched.

## Changing the contracts

A widening of either contract is a protocol change here; what it means for a consumer's results is the consumer's to decide.
